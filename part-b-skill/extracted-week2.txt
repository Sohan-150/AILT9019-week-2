Figure 1, anatomy of an AI agent. Context is what the LLM reads; skills are reusable instructions you write; MCP tools 
are external calls it may make. 
Why this matters: a plain chat and an agent differ only in the right half of this figure. Same LLM, 
but the agent is given your instructions as context, your skills to follow, and tools to call. That is 
what you are assembling this week. 
Part A · Context engineering (15 min) 
1. Open your AI coding tool (CodeBuddy or TRAE) in an empty folder. 
2. Write a one-line session instruction at the top of the chat. Example: 
You are helping me build a small Python tool. 
Keep answers short and show commands I can run. 
3. Ask one small task (e.g. “write a function that counts words in a file”). Then change only 
the instruction, e.g. add “always include a usage example”, and repeat the same task. 
4. Acceptance: you can explain in one sentence why the clearer instruction changed the result. 
Part B · Your first skill (15 min) 
1. Create a folder named my-skill with a file SKILL.md inside. 
2. In SKILL.md, write what the skill is for, when to use it, and one concrete step. A complete 
working example: 
# Meeting-notes cleaner 
Purpose: turn rough meeting notes into a short action list. 
Use when: the user pastes text marked [MEETING NOTES]. 
Steps: (1) list every action item as `owner, task, due date`, 
(2) list open questions separately, (3) change nothing else. 
3. Tell the AI tool to use your skill for a task (paste a short fake meeting note marked 
[MEETING NOTES] and ask it to clean it). 
4. Acceptance: the output follows the exact format your SKILL.md specifies, action lines look 
like “owner, task, due date”.

1. Follow the tutorial demo to register a small MCP server, a tool that returns a value, such as

2. Ask the agent to call that tool and report the result. A request that forces a tool call looks

3. Acceptance: the agent shows you real output from the tool, and you can name which part of

Part D · Run Pi Agent (25 min) 
1. Install Pi Agent (see the tutorial slides): 
npm install -g @earendil-works/pi-coding-agent 
2. Configure a model provider and start pi in a practice folder. 
3. Ask it to create a small script, run the script, and explain what it changed. 
4. Copy your skill from Part B into .pi/skills/ and repeat Part B inside Pi Agent. 
5. Acceptance: Pi Agent runs on your machine and uses your skill in a session. 
Part E · Push to GitHub (10 min) 
1. Push the practice folder (or a small project you started) to a GitHub repository you created 
this week. 
2. Acceptance: a fresh clone of your repository contains the files you built, test it: clone into a 
second folder and check the files are there.

Proposal requirements 
A brief example is provided in the proposal template (blue text, topic idea #3 Budget -policy Q&A 
only). Proposal writing must follow the section titles in that template. The table below states what 
each section should contain. Sample proposals, the idea list, and further advice are in the parts after 
this table. 
Section Requirement 
1. Background One primary user group, the concrete task, the current pain, and why the 
project is worth building this semester (motivation). Name a target — who it is 
for, and who or what it is not for. State where the idea comes from: which 
topic-list idea(s) and how far they were adapted, an external idea, or an 
original idea. A context figure is optional. 
2. Project pipeline A clear end-to-end path: how a request becomes a useful result (problem 
formulation + method). Say what the team will actually build. A pipeline 
diagram is encouraged. Data or tools belong here if they are part of the 
method (no separate Data section). 
3. Evaluation and test How the team will tell whether the project works. Choose a test style that fits 
the product (task set, walkthrough, comparison, refusal cases, etc.) and state 
what “good enough” means. Include at least one case the system should fail 
safely or refuse. Do not invent a method that cannot be run this semester. 
4. Distribution and 
accessibility 
How someone else can open and use the app, as they apply: (1) getting a 
model / AI API running without a painful setup; (2) whether a person with 
little or no coding background can complete a first successful use from the 
README or UI; (3) whether the work can sit in more than one agent 
environment (skill file, MCP tool, or another coding agent) if that is in scope. 
This is access and hand-off, not a full reproducibility recipe. 
5. Ethics and risks An explicit “does not” — what the product will refuse to do or claim — plus 
main misuse or failure risks and how they are mitigated (disclaimers, human 
hand-off, data limits). Peer reviewers should be able to quote the “does not” 
in one or two lines. 
6. Checkpoints Two parts. (A) Acceptance items: must-have (the demo fails without these) 
and should-have (only if time allows). (B) A timeline to the Week 4 draft and a 
little beyond. A timeline figure is encouraged. Keep must-have small enough 
to finish.

Topic idea list

Challenging — about build and evaluation difficulty this semester, not how unusual the topic is.

How to choose (do this before Week 3) 
1. Pick 2–3 ideas that feel interesting, then write one sentence per idea naming the single user 
group and single task. 
2. For each, name the dataset in one line, source plus permission to use (public, licensed, or 
self-curated). If you cannot name it, the idea is not ready. 
3. Match the Easy / Medium / Challenging band to your team’s experience; a finished Easy 
project beats an unfinished Challenging one. 
4. Avoid the crowd: a third of the cohort building the same project helps nobody.
